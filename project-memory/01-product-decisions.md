# 产品与交互决策

> 读取场景：产品范围、命名、信息架构、交互原则、数据边界。这里只保留当前有效决定。

## 产品定位

- 产品展示名已由用户确认采用 Luma，源于光亮意象。`brand-config.js` 统一管理名称与浏览器标题，`daylight-ui.js` 管理品牌标志；后续更名不逐页替换。GitHub 仓库已按用户要求改为 `awiggy/luma`；新增 `打开Luma.command`，旧启动入口保留。数据目录和 API 身份保持兼容，不迁移已有档案。
- 当前核心：四柱八字、塔罗占问、紫微斗数校盘、双档案合缘。
- 共同基础：出生档案、历史结果、确定性计算优先、用户已选定的“日光之间”视觉系统；全文使用同一无衬线字体栈，不再混用衬线和等宽字体。
- 产品原则：计算与 AI 解读分离。历法、四柱、大运、流年、神煞、紫微星曜及合缘结构证据由确定性引擎产生；AI 只能解释已有结果。
- 表达边界：传统文化研究与娱乐参考；不替代医疗、法律、投资或现实专业判断；避免恐吓、宿命和关系结局断言。

## 信息架构

- 主页使用四柱八字、塔罗占问、紫微斗数三张可点击、拖动、方向键切换的卡片；卡片箭头和子功能标签直接进入真实工作流，不再打开概念预览。
- 仅保留顶部导航，不使用底部功能导航。
- Logo 是独立主页入口；体系切换与体系内功能导航互相独立。
- 四柱体系内包含：命盘研判、岁运时间轴、问一件事、合缘。
- 塔罗和紫微各有体系内导航；用户档案是独立页面。
- 洞见/使用说明、设计理念各自独立；正式内容未确定时不要混入伪正式占位内容。

## 出生档案

- 全产品统一使用“出生档案”；新增操作统一为“新增出生档案”。
- 编辑弹窗顶部为阳历/阴历/四柱；阳历与阴历采用左右等宽双列。
- 左列：名称、日期时间、性别；右列：出生城市、地图、时区、北京时间/真太阳时。
- 地区输入与地图共用唯一定位结果；真太阳时复用同一经纬度。
- 地图支持选点、设备定位、全屏及 Esc 退出。
- 阳历、阴历、四柱由同一排盘引擎双向换算并同步。
- 阴历使用初一、初十、十一、二十、廿一、三十等传统写法，并处理闰月。
- 四柱反查允许多个候选公历日期，由用户选择。
- 历史资料按出生信息自动去重，支持搜索、编辑和单条删除。
- 编辑必须携带原档案 ID 原地更新；新增必须清空编辑 ID。

## 结果与历史

- 已生成分析必须缓存，重开同一记录不得再次调用模型或生成不同结果。
- 问事、塔罗、紫微和合缘均应明确区分新建流程与历史重开。
- 合缘使用两份已有出生档案与确定性合冲/五行证据；分数仅用于整理结构，不代表关系好坏或结局。
- 塔罗必须先有明确问题才能抽牌；抽牌结果保存 seed 和 time factor，以便复现。

## 本地与未来账户

- 当前数据本机优先；SQLite 保存档案与缓存，API Key 由 macOS 钥匙串保存。
- 用户不应每次重新填写 API Key。
- 登录、账户和跨设备云同步边界尚未确定，进入线上阶段后再做产品决策。
